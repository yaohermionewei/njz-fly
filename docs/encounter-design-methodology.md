# NJZ 飞行游戏：障碍、敌人和金币的关卡设计方法

更新时间：2026-09-12

> **已过时（2026-10-28）**：旧的六航道 encounter 系统已被 `components/levelSegments.ts` 的手工片段库 + 导演取代，设计依据见 `docs/关卡布局设计研究.md`。本文仅作历史参考。

这份文档针对当前横版无限卷轴飞行玩法。参考图中的兔子、曲奇和其他敌人只用于提炼设计方法；本项目仍然只有金币、站在水管上的猪，以及 Blue 的上下移动和射击。

## 先判断当前系统为什么会重复

`FlightGame.tsx` 已经具备六条航道、13 个 encounter、镜像、确定性随机、可达性验证和多种金币曲线。这些是很好的基础，但生成器目前仍然是“挑一个模板，再做镜像、时间抖动和金币布局”。模板的事件结构（哪条航道被挡、哪条是 preferred lane）没有变化，因此玩家实际识别到的仍是少数几种动作：上下切换、左右夹逼、连续之字形和中间停留。

金币也大多是事件路线的装饰：`line/diagonal/arc/zigzag/wave/grid/layers` 只改变曲线，尚未改变决策。例如金币没有明确区分安全路线、射击路线和高风险奖励路线，猪也没有成为“先射击还是先躲避”的选择题。要增加有趣度，应把生成单位从“障碍物列表”提升为“带目的的节拍（beat）”。

## 从参考图沉淀出的可迁移规则

参考图虽然机制不同，但反复出现以下关系：

| 图中现象 | 可迁移到本项目的规则 |
| --- | --- |
| 单条长水管，敌人排成一列 | 用作瞄准教学或射击节拍；第一次出现时给出清晰的射击窗口。 |
| 上下多行敌人和曲奇交错 | 让玩家在“换航道吃金币”和“留在当前航道射击”之间选择；金币路线不应总是唯一安全路线。 |
| 顶部/底部水管，中间留出通道 | 形成可读的承诺：先选中间路线，再在下一拍决定向上或向下。不要在同一时间把所有航道封死。 |
| 画面中散落的金币 | 用作探索奖励或视线引导；散落金币不应与必经碰撞盒重叠。 |
| 水管上的敌人 | 水管负责空间限制，猪负责注意力和射击决策；两者叠加时要保留一条不用射击也能通过的路线。 |
| 多个垂直水管组成门/笼 | 把它当作高强度节拍或奖励房间，提前一拍显示结构，出口必须有恢复空间。 |
| 倾斜水管和移动敌人 | 只改变视觉节奏或敌人的扫动范围，不要同时引入全新的碰撞规则。 |

可以把每个 encounter 写成四个连续小节：

1. **预告（telegraph）**：只出现一个简单的水管或猪，让玩家读懂方向和目标。
2. **执行（test）**：要求一次上下移动、一次保持航道，或在短窗口内射击。
3. **转折（twist）**：改变猪的位置、金币的风险路线或水管的朝向，但保留已学会的规则。
4. **释放（relief）**：至少留出约 0.8–1.2 秒的低压力空间，用于恢复和确认奖励。

这套节拍来自《The Level Design Book》对 pacing 和 beats 的定义：节拍是可独立理解的小块，pacing 需要安排信息、强度和休息。参考：[Pacing | The Level Design Book](https://book.leveldesignbook.com/process/preproduction/pacing)。

## 推荐的生成架构：节拍语法 + 约束筛选

不要继续单纯增加 `ENCOUNTER_PATTERNS` 的数量。建议将数据分成三层：

### 1. 原子动作（atoms）

每个原子动作只有一个目的，参数化而不是复制整段事件：

- `gate`：一条水管挡住 1–2 条航道，定义目标航道。
- `switch`：要求从当前航道切到相邻或隔一条的航道。
- `shootWindow`：猪站在水平水管上，射击窗口与安全航道分离。
- `patrol`：猪在水管上左右扫动，扫动范围不超过 1.2 条航道。
- `pincer`：上下两侧同时施压，中间保留一条明确路线。
- `cage`：水管围出奖励空间，金币在笼内，出口先空出一拍。
- `breather`：无伤害实体，仅放置少量金币。

### 2. 节拍语法（beats）

用短序列组合原子动作，每个序列标注意图和强度。例如：

```ts
{
  id: 'teach-shoot-then-switch',
  beats: [
    { atom: 'shootWindow', duration: 0.95, intensity: 1 },
    { atom: 'switch', direction: 'down', duration: 1.1, intensity: 2 },
    { atom: 'breather', duration: 1.0, intensity: 0 },
  ],
  reward: { route: 'post-shot', coins: 5 },
}
```

同一语法可以通过起始航道、镜像、猪的扫动方向、水管朝向、金币路线和时间间隔产生多个可辨识变体。这样增加的是决策数量，而不是只增加随机坐标。

### 3. 章节编排（director）

按距离维护强度预算和最近历史：

- 0–1800 px：只使用 `gate`、单次 `switch`、静止猪；每个 encounter 只考一个技能。
- 1800–5200 px：允许 `shootWindow + switch`、`patrol`、双路线金币；连续两个高强度节拍之间插入 `breather`。
- 5200 px 以后：允许 `pincer`、`cage`、连续两次决策，但仍需保留可达航道和出口恢复。
- 最近 4 个 encounter 不重复 `family`；最近 2 个 encounter 不重复“主要动作方向”（上/下/中间）。
- 强度序列建议使用 `0,1,2,1,3,0/1` 的波形，而不是持续递增。

## 约束和公平性检查

每个候选节拍生成后，先模拟再显示。当前代码已有 `validateEncounter` 和 `validateCollectibleTrails`，建议补充以下约束：

### 可玩性

- 每一事件至少有 1 条安全航道；连续事件的目标航道必须在玩家移动能力内。
- 用当前参数计算反应时间：`START_SPEED=285`、巡航约 `410 px/s`，预告距离至少 300 px 时约有 0.73 秒；高强度节拍建议将预告距离提高到 360–440 px。
- 相邻碰撞盒之间保留角色宽度再加 12–20 px 的余量；旋转水管按真实包围盒检查。
- 猪的射击窗口必须大于一次冷却（280 ms）加瞄准余量，避免“看见即撞上”。
- 任何金币轨迹都不能强迫玩家穿过水管或猪；高风险金币可以靠近危险，但必须有清晰的安全替代路线。

### 可读性

- 同一拍最多引入一种新规则：水管方向、猪的移动或金币风险三者不要同时首次出现。
- 在猪移动或水管组合前留出空拍或低密度金币，给玩家读图时间。
- 碰撞盒与视觉造型分离：先画出 debug 矩形验证公平，再替换正式素材。

### 多样性

每次生成记录以下标签，而不是只记录 `patternId`：

```ts
type EncounterTags = {
  family: 'gate' | 'switch' | 'shoot' | 'patrol' | 'pincer' | 'cage' | 'breather';
  direction: 'up' | 'down' | 'center' | 'alternating';
  rewardRoute: 'safe' | 'risky' | 'post-shot' | 'split';
  intensity: 0 | 1 | 2 | 3;
};
```

拒绝与最近历史在 family、direction、rewardRoute 三个维度同时相同的候选。每个种子生成 100 个 encounter 后，统计 family 分布和路线分布；任何单一 family 超过 35% 都说明变化不足。

## 金币和猪如何形成真正的选择

金币暂时只有一种类型也足够做出层次，关键是它表达不同的风险：

- **安全线**：沿当前可达航道，数量少，帮助新玩家通过。
- **射击线**：猪出现前先给 2–3 枚金币，猪被击杀后再给完整奖励；玩家会自然学会“先瞄准”。
- **风险线**：靠近水管边缘或需要多一次换道，数量更多，但绝不堵死安全线。
- **分叉线**：上下两条都可行，一条更容易收集，一条更适合留在原航道射击；在出口合流。
- **连击线**：连续收集 4–8 枚后给一个明显的空拍，奖励节奏感而不是无限堆叠。

猪的站位应服务于金币选择：猪永远站在水平水管上，且至少有一个“不射击也能通过”的路线；当猪位于奖励线时，击杀应当打开更高价值路线，而不是单纯把障碍删掉。

## 建议先实现的 12 个节拍族

这不是 12 个固定关卡，而是 12 个可参数化的族：

1. 单门 + 安全线
2. 单门 + 上下分叉金币
3. 预告猪 + 射击线 + 释放
4. 预告猪 + 下切换
5. 预告猪 + 上切换
6. 中间保持 + 上下风险金币
7. 双门交替（上、下）
8. 双门同向（连续向上或连续向下）
9. 中间猪巡逻 + 两侧安全
10. 夹逼门 + 中央金币笼
11. 击杀后奖励线
12. 高强度节拍后 breather

每一族至少配置 4 个参数变体：起始航道、镜像方向、时间间隔、金币路线。这样首批就有约 48 个可辨识 encounter，而不是 13 个模板的轻微抖动。

## 工具选择

### 现在最适合：继续使用 TypeScript 数据驱动

当前项目是 React + Vite + Canvas，实体和碰撞已经在 `FlightGame.tsx` 中完成。短期不建议引入完整引擎；把 atoms、beats 和约束拆成独立的 `encounters.ts`，增加一个可视化 debug 模式和固定 seed 导出，就能快速迭代。

### LDtk：适合人工设计节拍原型

[LDtk](https://ldtk.io/) 是开源的 2D 关卡编辑器，支持自定义实体和类型属性，并导出 JSON。它适合把“水管、猪、金币、玩家起点”拖到六航道网格上，再导出一批人工批准的节拍。它不是无限运行时生成器，建议作为离线 authoring 工具，最终仍由 TypeScript 生成和验证。

### Tiled：适合场景和长地图

[Tiled](https://www.mapeditor.org/) 支持对象层、自定义属性和无限地图；[Infinite Maps 文档](https://doc.mapeditor.org/en/stable/manual/using-infinite-maps/)说明其画布可以自动扩展。它更适合城市背景、静态章节或需要逐格摆放的水管组合。Tiled 主程序为 GPL，若把其库嵌入产品需单独评估许可证；仅用编辑器导出数据通常更简单。

### Wave Function Collapse：只用于局部形态，不负责公平性

[mxgmn/WaveFunctionCollapse](https://github.com/mxgmn/WaveFunctionCollapse) 的 MIT 实现根据示例提取局部 NxN 模式，并支持约束。它可以帮助生成水管装饰、背景拼接或局部视觉变体，但局部相似性不会自动保证“玩家可达”。必须在 WFC 输出后运行本项目的航道可达性和碰撞验证；不要用它直接决定猪和金币的位置。

### 可参考的开源实现

- [SS12220/Endless-Runner](https://github.com/SS12220/Endless-Runner)：Unity 无限跑酷的程序化关卡示例，适合查看分段生成和对象回收思路；复用代码前先核对仓库许可证。
- [D'arcy Sullivan – Endless Runner: Procedural Generation](https://sully745.github.io/EndlessRunner-Procedural-Generation/)：展示把跑酷内容拆成程序化片段的教学项目，适合比较不同片段的拼接方式。
- [Procedural Content Generation in Games: A Survey](https://arxiv.org/abs/2410.15644)：综述 constructive、Markov、WFC、搜索和进化方法，明确指出生成算法需要配合评价函数；这正是本项目“生成候选 → 模拟验证 → 选择”的依据。

## 验证面板应该记录什么

给开发模式增加一个 encounter inspector，每次显示 seed、family、强度、事件时间线、六条航道的安全/危险状态和金币路线。跑 30–60 秒后导出：

- 受伤率、死亡前平均距离、每个 family 的出现次数。
- 每个 encounter 的安全路线数量、最短换道距离、最短反应时间。
- 金币收集率，以及选择风险线后获得的额外金币。
- 猪出现时的射击成功率和错过率。
- 最近 20 个 encounter 的 family/direction/rewardRoute 重复度。

建议的第一版验收线：安全路线始终 ≥1；最短反应时间 ≥0.70 秒；高强度节拍后 1.0 秒内不再出现伤害盒；单一 family 占比 ≤35%；风险线的平均金币收益至少比安全线高 30%。这些数值不是最终平衡，只是用来快速发现“无聊”或“不公平”的候选。

## 推荐落地顺序

1. 把当前 `ENCOUNTER_PATTERNS` 拆成 atoms、beats 和 director 标签，保持现有碰撞和素材不变。
2. 先实现 12 个节拍族中的前 6 个，加入安全线/射击线/风险线金币角色。
3. 将 `validateEncounter` 扩展为反应时间、恢复空拍和风险路线验证。
4. 增加 seed、节拍标签和 debug inspector，连续试玩并记录指标。
5. 只有当数据表明仍然重复时，再增加新 atom；不要先继续添加更多几何模板。
6. 稳定后再考虑 LDtk/Tiled 的离线 authoring，导出的数据仍需经过同一套验证器。
